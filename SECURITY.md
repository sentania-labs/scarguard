# Security Model

ScarGuard controls physical actuators (sprinklers, sirens, lights) in a
residential yard. Its security model has to reflect that — "admin can do
X" is fine for a SaaS dashboard, but here admin actions open solenoid
valves for real. This document describes the trust boundaries, how
secrets are handled, and what to do when things go wrong.

## Trust boundaries

```
                ┌──────────────────────────────────────────┐
                │               Internet                    │
                └────────────────────┬─────────────────────┘
                                     │  80/443
                                     ▼
                ┌──────────────────────────────────────────┐
                │  Caddy (TLS termination + reverse proxy) │
                │  • only ingress to the FastAPI web app   │
                │  • enforces HSTS + CSP + Permissions-    │
                │    Policy + no-probe edge denies         │
                └────────────────────┬─────────────────────┘
                                     │  docker internal net
       ┌─────────────────────────────┼─────────────────────────┐
       ▼                             ▼                         ▼
  ┌──────────┐   HMAC-signed    ┌─────────┐             ┌────────────┐
  │ Detector │  Redis pub/sub   │ Redis   │             │    Web     │
  │          ├─────────────────▶│ auth'd  │◀────────────│ FastAPI    │
  └──────────┘                  │ pub/sub │             │ + Jinja    │
                                └────┬────┘             └─────┬──────┘
                                     │                        │
                                     ▼                        ▼
                             ┌───────────────┐       ┌───────────────┐
                             │   Deterrent   │       │  SQLite DBs   │
                             │  (Tuya Cloud) │       │  + snapshots  │
                             └───────────────┘       └───────────────┘
```

| Boundary | Trust assumption |
|---|---|
| Caddy ↔ Internet | **Untrusted.** Caddy is the only ingress; the web container has no host port binding by default. |
| Caddy ↔ Web | **Trusted.** Caddy is the only peer `web` speaks HTTP with. Since v1.14, `forwarded_allow_ips` is scoped to the Docker bridge CIDRs (overridable via `SCARGUARD_TRUSTED_PROXIES`). |
| Web ↔ Detector/Deterrent/Notifier | **Mutually-trusted peers on the internal Docker network.** Redis pub/sub is password-gated (random 32-char credential generated by `setup.sh`). Detection events are additionally HMAC-SHA256-signed (`DETECTION_HMAC_KEY`) so a compromised sidecar can't inject fake detections that trigger physical actuation. |
| Web ↔ SQLite DBs | **Trusted writer, RO readers.** Only `web` writes `auth.db`; only the detector writes `scarguard.db` event/metric rows (web writes feedback and config-backup rows); only `deterrent` writes `deterrent.db`. Other services mount `/data:ro`. |
| Docker socket | Exposed only to the `training-controller` sidecar when the opt-in training profile is active. Its dedicated credential is shared only with trainer; the API hard-codes lease operations for the single Compose detector service and accepts no container name or arbitrary Docker operation. `web`, `trainer`, and `log-streamer` have no Docker socket; log-streamer retains read-only proxy access. |

## Secrets handling

### At rest

As of v1.14, sensitive YAML fields are encrypted on disk via Fernet
(AES-128-CBC + HMAC-SHA256) with a `enc:v1:` prefix:

* `deterrent.tuya.api_key` / `api_secret`
* Channel `webhook_url`, `smtp_pass`, `auth_token`, `token`, `password`

The key lives at `/data/secret_key` (mode `0600`), generated on the
first web startup. Notifier and deterrent mount `/data` and load the
same key to decrypt at runtime.

**Upgrade behaviour:** existing plaintext secrets pass through on read
(no-op), and the first save after upgrade automatically re-encrypts them.
`v1.15` will drop the plaintext-passthrough code path and reject
unencrypted values — see `ROADMAP.md`.

**Rotation:** stop the web container, overwrite `/data/secret_key` with
a new Fernet key, restart. Pre-existing ciphertext becomes unreadable
and the affected fields will need to be re-entered in the admin UI
(which is the intent when you rotate). A proper
`scripts/rotate-secret-key.sh` that re-encrypts in place is tracked as
v1.15 work.

### Not at rest

* `REDIS_PASSWORD` — `.env` file on the host. Treat the host as secret-grade.
* `DETECTION_HMAC_KEY` — same `.env`. Regenerate and restart all
  services if you suspect leakage.
* `TRAINING_CONTROLLER_TOKEN` — same `.env`, exposed only to trainer and the
  lifecycle controller. Rotate it if either service or the host is compromised;
  unauthenticated controller lifecycle requests fail closed.
* `BOOTSTRAP_TOKEN` — `/data/bootstrap_token`. Deleted on first successful
  `/setup` POST; never valid again after first admin creation.
* Session cookies — bcrypt-hashed in `auth.db`; HttpOnly + SameSite=Strict;
  `Secure` flag set when the request is TLS.

### First-run bootstrap

Pre-v1.14, a fresh deployment exposed to the internet before the
operator seeded an admin account could be claimed by any caller. v1.14
closes this with a bootstrap token written to `/data/bootstrap_token`
and logged to stdout at startup:

```
$ docker compose logs web | grep 'First-run'
═══════════════════════════════════════════════════════════
  First-run setup — complete within 24 hours:
    Browse to: /setup?token=<value>
  Token also stored at /data/bootstrap_token (chmod 600).
═══════════════════════════════════════════════════════════
```

The operator uses the URL to create the first admin. The token file is
deleted on success; subsequent attempts to hit `/setup` are
permanently closed by the `users_exist` check.

Env var `SCARGUARD_BOOTSTRAP_TOKEN` overrides the file for operators
who seed credentials through a config-management tool.

## Recommended deployment posture

**Home LAN, Let's Encrypt TLS (recommended):**
- `tls.mode = auto` with a public DNS name → Caddy fetches and renews
  a cert automatically.
- Firewall open 80/443 to the internet; web port (8080) has no host
  binding.
- Full-disk encryption on the Jetson SD card strongly recommended —
  `.env` and `/data/secret_key` are the authoritative secret
  material and live on that device.

**Home LAN, no internet exposure:**
- `tls.mode = manual` with a self-signed cert, or `tls.mode = off` if
  you truly trust the LAN. Without HTTPS, HSTS is disabled; the
  `secure` flag on session cookies is also disabled.

**Jetson with SD-card boot:**
- Point `/data` at a USB SSD. SD cards fail without warning; when they
  fail, you lose detection history, auth, and the deterrent audit
  trail. See `BACKUP.md` for the backup sidecar and
  `scripts/restore-from-backup.sh`.

## Physical-safety safeguards

ScarGuard enforces actuation bounds at four layers:

1. **Web API validation** — `duration_sec` is rejected with 400 if
   outside `[0.5, 15.0]` seconds for test-fire.
2. **Deterrent request handler** — defence-in-depth clamp using the
   same constants.
3. **Cloud controller** — defence-in-depth clamp again plus a
   `threading.Timer` watchdog that fires unconditional OFF at
   `MAX_ACTUATION_SEC = 60` from the ON command, regardless of what
   the caller or the Tuya client do.
4. **Reconciliation loop** — every 30 seconds the deterrent polls
   every enabled device's status and force-OFFs any device reporting
   ON while not actively being driven.

If all four somehow fail, the `/admin/deterrent/force-off` endpoint
sends OFF to every configured device unconditionally. See
`docs/EMERGENCY_OFF.md` for the full runbook.

**Hardware belt-and-suspenders:** Tuya smart hose-timer valves and
plugs can be configured with a firmware-side auto-off timeout via the
Tuya app. Use it. It's the only safeguard that survives a full
ScarGuard host failure.

## Detection-bus authentication

Every detection event published on `scarguard:detections` carries an
HMAC-SHA256 signature keyed on `DETECTION_HMAC_KEY`. Detector signs;
deterrent and notifier verify before acting. An event with an invalid
or missing signature is rejected — the deterrent never fires on it,
the notifier never dispatches it. This closes the "compromised sidecar
injects a fake heron detection" attack.

Backwards compatibility: if the key is absent (older `.env` files),
services log a loud warning and accept unsigned events, so in-place
upgrades don't drop detection traffic. Running `setup.sh` on an
existing install backfills the key; services restart picks it up.

## Rate limiting

Physical-control endpoints and config endpoints enforce fixed-window
rate limits (Redis-backed counters) so a stolen admin session can't
hammer the hardware:

| Endpoint | Limit |
|---|---|
| `POST /admin/deterrent/test-fire` | 10/min per principal |
| `POST /admin/deterrent/force-off` | 5/min per principal |
| `POST /arm` / `/disarm` | 30/min per principal |
| `POST /deterrent-enable` / `-disable` | 30/min per principal |
| `POST /config` / `/config/structured` | 20/min per principal |
| `POST /models` (upload) | 10/hour per principal |
| `POST /feedback/{token}` (public) | 30/hour per IP |
| `POST /admin/db-backups/trigger` | 10 per 5 minutes per principal |

Principal is `user:<id>` when authenticated; falls back to `ip:<host>`
otherwise. Fails open on Redis error (better to let legitimate traffic
through during a Redis outage than to hard-block the UI).

## Known scope gaps (as of v1.14)

The items below were considered during the v1.14 hardening review and
deferred with explicit reasoning. See `ROADMAP.md` for the full list.

* **CSP still allows `'unsafe-inline'` for `script-src`.** Tightening
  requires a nonce migration across every inline-script template. HSTS
  and Permissions-Policy are in place.
* **htmx and Chart.js load from unpkg.com.** CSP allows the host;
  vendoring them into `/static/vendor/` to drop the third-party host is
  future work.
* **SSE streams (`/events/stream`, `/feed/stream`, `/admin/logs/stream`,
  `/admin/stats/stream`) have no concurrent-connection cap.** Request
  counters don't fit long-lived streams; a connection-tracking primitive
  is needed.
* **Actuation audit trail is not tamper-evident.** Entries carry
  `request_id` and per-device success flags, but not a signed hash
  chain. High-effort, low-marginal-value for a single-operator
  deployment.
* **Web service is a single replica** and the compose file assumes
  that. Multi-replica would need a shared session store.

If you build on ScarGuard in a more-exposed environment than a home
LAN, please read the deferred list and file issues for whatever you
want prioritised.
